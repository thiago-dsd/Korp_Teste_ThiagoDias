# Performance

What was measured, what it cost, what was changed and what was deliberately left alone.

Numbers come from `backend/cmd/loadgen`, a dependency-free load generator that signs in once and
keeps a fixed number of requests in flight. It reports the distribution rather than an average,
because an average hides exactly the requests somebody would complain about.

## How to reproduce

```bash
make infra-up
RATE_LIMIT_ENABLED=false make run-identity   # and run-stock, run-billing
cd backend
go run ./cmd/loadgen -seed 5000                                   # catalogue to work against
go run ./cmd/loadgen -scenario catalogue     -concurrency 32 -duration 20s
go run ./cmd/loadgen -scenario invoice-write -concurrency 16 -duration 15s -items 50
```

Throttling is turned off on purpose: with it on the numbers describe the rate limiter, not the
system. Everything below ran on one laptop with PostgreSQL and RabbitMQ in Docker, services and
load generator on the host, so the absolute figures are only meaningful next to each other.

## Environment used for the numbers below

5 000 products for the throughput runs, 50 000 for the scaling check, ~78 000 invoices in the
billing database, concurrency as noted per scenario.

## Results

| Scenario | Concurrency | Throughput | p50 | p95 | p99 | PostgreSQL CPU |
| --- | --- | --- | --- | --- | --- | --- |
| `catalogue-out` — balance filter, sorted | 32 | 21 700/s | 1.4 ms | 1.9 ms | 2.1 ms | 180% |
| `invoice-list` — status filter, paged | 32 | 13 000/s | 2.4 ms | 2.9 ms | 3.2 ms | 129% |
| `catalogue` — text search | 32 | 2 390/s | 13.2 ms | 16.0 ms | 17.6 ms | 908% |
| `invoice-write` — 3 items | 16 | 2 050/s | 7.6 ms | 10.0 ms | 12.4 ms | 172% |
| `invoice-write` — 50 items | 16 | 1 240/s | 11.9 ms | 19.7 ms | 27.8 ms | 311% |
| `bulk-adjust` — 50 movements, atomic | 8 | 367/s | 21.2 ms | 25.0 ms | 40.5 ms | 271% |

Asynchronous printing, measured end to end (accepted → outbox → RabbitMQ → debit → answer →
invoice closed): **5 000 invoices accepted in 1 s and fully closed ~10 s later**, about 500
invoices per second. Peak queue depth 1 736, drained without accumulating; RabbitMQ stayed at
114 MiB. The consumer handles one message at a time per queue and that is still far from being
the limit, so it was left as it is.

## What was changed

### Invoice items were inserted one round trip at a time

`Store.Create` looped over the items and ran one `INSERT ... RETURNING` per line, inside the
transaction. An invoice may carry a hundred products, so a write that should cost one round trip
cost a hundred. The signature was visible in the measurements: latency grew by ~0.6 ms per item.

They now go in with a single statement over parallel arrays, with the ids generated by the
service so each stored row can still be matched to the item it came from.

| Invoice size | Before | After |
| --- | --- | --- |
| 50 items | 367/s · p50 38.2 ms · p95 81.1 ms · p99 115.3 ms | 1 240/s · p50 11.9 ms · p95 19.7 ms · p99 27.8 ms |
| 3 items | 1 523/s · p50 10.3 ms · p99 17.3 ms | 2 050/s · p50 7.6 ms · p99 12.4 ms |

**3.4x the throughput and a quarter of the p99** on large invoices, and a smaller but real gain
on small ones.

## What was measured and deliberately not changed

### Text search does not use the trigram indexes

`GET /products?search=` degrades linearly with the size of the catalogue:

| Catalogue | Time | Buffers read | Rows discarded |
| --- | --- | --- | --- |
| 5 000 products | 3.3 ms | 748 | 3 562 |
| 50 000 products | 17.2 ms | 11 235 | 39 116 |

The planner ignores the `gin_trgm_ops` indexes. `ORDER BY upper(code) LIMIT 21` makes walking the
ordered index and filtering look cheap, because it assumes the matches are spread evenly and it
will collect 21 of them early. When the matching rows sort late it walks most of the table first.

Forcing the trigram path is 3.3x faster and reads 22x fewer buffers **for a selective term**
(5.2 ms, 505 buffers at 50 000 products). It is also the wrong plan for a broad one: searching a
term that matches most of the catalogue costs 16 buffers today, because the scan stops after the
first page, against 1 270 buffers through the index. Making narrow searches 3x faster by making
broad ones 80x slower is not an improvement, so nothing was changed.

At the volume this system is built for the current behaviour is comfortable: 2 390 searches per
second with a p99 of 17.6 ms. The note is here so that whoever grows the catalogue past ~50 000
products knows where the cost is and what the options are — a combined `search_text` generated
column with a single trigram index, chosen only when the term is selective enough to deserve it.

### Things that were suspected and turned out to be fine

- **N+1 on the listings.** `Store.List` already loads a page of invoices with one query and every
  item of that page with a second one; it does not grow with the page size.
- **The single-threaded consumer.** One message at a time per queue still moves ~500 invoices per
  second end to end. Adding concurrency here would trade the ordering guarantee for capacity that
  is not needed.
- **Queue build-up.** The queue peaked at 1 736 messages under a burst of 5 000 prints and
  drained in seconds, with flat broker memory.
- **Balance and status filters.** Four buffers per query and flat as the tables grow, which is
  what the indexes added with the filters were for.

## Budgets for catching regressions

Same machine, same seeded volume, throttling off. A run outside these bounds means something got
slower and should be explained before it ships:

| Scenario | Throughput floor | p99 ceiling |
| --- | --- | --- |
| `catalogue-out` | 15 000/s | 5 ms |
| `invoice-list` | 9 000/s | 6 ms |
| `catalogue` | 1 800/s | 25 ms |
| `invoice-write -items 3` | 1 500/s | 20 ms |
| `invoice-write -items 50` | 900/s | 45 ms |
| `bulk-adjust -batch 50` | 250/s | 60 ms |
| async printing | 300 invoices/s | queue drains, never grows across runs |

The floors sit roughly 25-30% under what was measured, so ordinary noise on a busy laptop does
not cause false alarms while a real regression — an index dropped, a loop of round trips
reintroduced, a lock added on a hot path — moves the numbers far more than that.
